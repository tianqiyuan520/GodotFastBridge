## 一、收益模型

### 1.1 成本构成（已由引擎源码确证，见机制文档）

```
一次「C# 数组参数调用」的既有成本：
  ① 原生 resize(N·E) 分配               ← GFB 可省
  ② memcpy(N·E) 到临时容器             ← GFB 可省（当调用方本就有连续内存）
  ③ 调用返回后释放临时容器              ← GFB 可省
  ④ 引擎/驱动内部再拷一次到 GPU/Image    ← 不可省
出向（回读）：
  ⑤ 原生把数据装进返回容器               ← 不可省（返回类型即容器）
  ⑥ 托管 new T[N] + MemoryCopy          ← GFB 可省
GFB 自身新增：
  ⑦ 把调用方数据填进「复用容器」的一次 memcpy ← 必付（与 ② 同量级）
```

**净收益 = ① + ③ +（② 若调用方本来要中转）+ ⑥ − ⑦ 的额外部分**
其中 ⑦ 与 ② 同量级，因此**净收益主要来自「分配/释放」与「出向的托管分配」**；只有当调用方**本来就有一次多余中转**（如 `float[]` → `byte[]` + `BlockCopy`）时，才额外赚到一次完整拷贝。

### 1.2 带宽锚点（本项目唯一的实测数字）

来源：`ComputeShaderBattleSimulation/docs/CPU-百万同屏-现状沉淀.md:359`

```
[M-2] 纹理上传 = 2.74 ms（桥内 fill = 0.717 ms, submit = 1.389 ms）
payload = 8~16 MB
⇒ memcpy 有效带宽 ≈ 11 ~ 22 GB/s（取 15 GB/s 作为换算基准）
```

| payload | 单次拷贝耗时 |
|---|---|
| 32 MB | 1.5 ~ 2.9 ms |
| 16 MB | 0.7 ~ 1.5 ms |
| 8 MB | 0.36 ~ 0.73 ms |
| 4 MB | 0.18 ~ 0.36 ms |
| 1.44 MB | 0.07 ~ 0.13 ms |
| 484 KB | 0.02 ~ 0.04 ms |
| < 256 KB | 噪声级（不建议接入） |

### 1.3 已确认的历史数字（强度不同，须区分）

| 数字 | 来源 | 可信度 |

### 1.4 M1 实测：Godot 内 A/B（已完成，debug host + release 导出）

**环境**：Godot 4.7-stable mono；NVIDIA RTX 4060 Laptop；30000 实例；
payload：SSBO 1406 KB / MultiMesh 937 KB / RD 纹理 4096 KB / Image 4096 KB；
每用例 20 次预热 + 200 次取样取最小值；vsync 关闭；
载体 `project/benchmark/Benchmark.cs` + `project/benchmark.tscn`，结果同时落盘 `user://gfb_bench.txt`。

- **debug host** = 编辑器二进制运行（`debug_build=True`），C# 程序集 Debug 配置但显式 `<Optimize>true</Optimize>`
- **release** = `--export-release "Windows Desktop"` 导出（release 模板 + release DLL + ExportRelease C# 程序集），`debug_build=False`

#### IN（提交）

| 用例 | C# 直接 | C# + 新数组/拷贝 | GFB 桥 | vs 直接 | vs 拷贝 |
|---|---|---|---|---|---|
| SSBO 1406 KB（`RenderingDevice.BufferUpdate`） | 230 ~ 360 µs | 309 ~ 477 µs | **57 ~ 78 µs** | **3.5 ~ 5.2×** | **5.3 ~ 6.8×** |
| MultiMesh 937 KB（`RenderingServer.MultimeshSetBuffer`） | 75 ~ 98 µs | 119 ~ 163 µs | **41 ~ 50 µs** | **1.7 ~ 1.9×** | **2.7 ~ 3.2×** |
| RD 纹理 4096 KB（`RenderingDevice.TextureUpdate`） | 857 ~ 1217 µs | — | **515 ~ 669 µs** | **1.6 ~ 1.8×** | — |
| Image 4096 KB（`Image.SetData` + `ImageTexture.Update`） | 846 ~ 1542 µs | — | 927 ~ 1294 µs | **0.85 ~ 1.19×（≈持平，偶有劣化）** | — |

#### OUT（回读）

| 用例 | C# 回读 | GFB `read_into` | 加速 | 托管分配 / 次 |
|---|---|---|---|---|
| SSBO 1406 KB | 509 ~ 602 µs | 403 ~ 467 µs | 1.11 ~ 1.29× | **1,440,024 B → 0 B** |
| MultiMesh 937 KB | 298 ~ 375 µs | 270 ~ 333 µs | 1.06 ~ 1.22× | **960,024 B → 0 B** |
| RD 纹理 4096 KB | 1285 ~ 1681 µs | 1154 ~ 1471 µs | 1.07 ~ 1.14× | **4,194,328 B → 0 B** |
| Image 4096 KB | 197 ~ 307 µs | **98 ~ 150 µs** | **1.61 ~ 2.18×** | **4,194,328 B → 0 B** |

**逐字节一致性**：SSBO / MultiMesh / RD 纹理 / Image 全部 `True`（所有运行）

#### 结论

1. **提交方向**：`BufferUpdate`（4.2×）、RD 纹理（1.7×）、MultiMesh（1.8×）收益明确且数倍级；debug 与 release 数字一致 ⇒ 收益来自原生侧（省掉每次调用的临时容器分配+拷贝），不是 JIT 假象。
2. **「僵尸式」写法**（每次 `new byte[]` + 拷贝）额外损失 20~45% 时间与 1.44 MB/次 LOH 分配，GFB 一并消掉。
3. **回读方向**：时间只快 1.1~2.2×，**真正的价值是托管分配归零**（1~4 MB/次 → 0 B），即消除 GC 压力。
4. **`Image.SetData` 写入方向无收益（0.85~1.19×）**：疑似 `Image::set_data` 直接接管传入容器（CoW），使其路径本身只有一次拷贝，GFB 的复用缓冲反而多付一次 memcpy。**该槽位仅推荐用于回读**。
5. **MultiMesh 物理插值提交已实测为劣化（0.38~0.46×，稳定复现），已从 ABI 移除**：`gfb_submit_interpolated` / `submit_interpolated` / `fast_bridge.h` 的 `float_buffer_prev` / C# 的 `SubmitInterpolated` 全部删除。若未来需要，必须先查清 `multimesh_set_buffer_interpolated` 在未启用物理插值时的引擎侧语义。

#### 换算成帧内占比（决定"值不值得用"）

| 场景 | payload/帧 | 收益/帧 | 占帧比 |
|---|---|---|---|
| 1M 单位（CSBS 类：位置+动画+渲染序） | ~16 MB | ~1.4 ms | **~14%**（其整帧 9.45 ms） |
| 30000 实例（僵尸大战僵尸类） | 1.44 MB + 两块 1.44 MB 分配 | 252 µs（vs 僵尸式） | **~1.5%**@60fps、5%@200fps |
| TerritorialWar 球纹理 | 968 KB（**Image 写入**） | **≈ 0** | **0%** |
| test 粒子纹理 | 3.06 MB（**Image 写入**） | **≈ 0** | **0%** |
| MassiveTextDemo MultiMesh | 4.6 MB | ~170 µs | 一次性触发，**无价值** |

> 换算基准：RD 纹理实测 171 µs/4 MB。

#### 被实测推翻的落点（同样重要）

1. **`Image.SetData` 写入方向无收益** → TerritorialWar 球纹理、test 粒子接收器、CSBS 的 RS 回退路径三处候选落点**全部作废**（此前估算的"0.06 ms/帧"是错的）。
2. **MultiMesh 的倍数只有 1.7~1.9×**，且其最大本地用例（MassiveTextDemo 4.6 MB）是一次性触发，不在每帧路径上。
3. **MultiMesh 物理插值提交稳定劣化 0.38~0.46×**，已从 ABI 移除。

#### 未覆盖

- 更大 payload（16 / 32 MB，百万实例）与 GDJobSystem 并行填充组合；
- **托管分配归零的 GC 收益（M0 第③项）与原生 `resize`/`free` 的孤立成本（第②项）仍未测量** —— 这是唯一可能上修 30k 级场景结论的一块；
- 帧内多槽混合提交对真实帧时间的贡献（当前只测单次调用耗时）。

## 三、引擎 API 面（哪些 API 在付费）

扫描方法：静态解析 `.../GodotSharp/Generated/`（脚本 `scan_api.ps1`，输出 `api_marshal.csv`）。

```
总量：511 个 API 方法 / 790 个重载走中转拷贝
      IN 方向 512 个重载（原生 resize + memcpy + 释放）
      OUT 方向 278 个重载（托管 new T[N] + MemoryCopy）

按承载类型：byte 193 / Vector2 158 / String 147 / int32 104 /
            float 66 / Vector3 64 / Color 28 / int64 24 / float64 6
按类型（去重 icall 方法）前 12：
            RenderingDevice 20 / RenderingServer 12 / Geometry2D 9 / OS 7 /
            DisplayServer 6 / CanvasItem 6 / TextServer 5 / MultiMesh 5 /
            Image 4 / FileAccess 4 / Polygon2D 4 / NavigationPolygon 4
PhysicsServer2D/3D：0 处（不在这一族）
```

### 3.2 T2：边际（不建议接入）

`TextServer` / `FontFile` / `SystemFont`（字形与字符串数组，问题是调用次数不是 payload）、`NavigationServer2D/3D`（路径 KB 级）、`NavigationPolygon` / `NavigationMesh`（烘焙期）、`SurfaceTool` / `MeshDataTool`（构建期）、`TileMapLayer.*TileMapData*`（加载/保存期）、`FileAccess`（IO）、网络族（`PacketPeer` / `StreamPeer` / `WebSocketPeer` / `ENet*` / `HttpClient`）、`Crypto` / `Hashing` / `Aes` / `Hmac`、`OS` / `DisplayServer`、`Geometry2D/3D`、`Gltf*`、`VoxelGI*` / `Lightmap*` / `Occluder*` / 各类 Shape（烘焙或一次性）、`*BufferCreate` 系列（创建期；若每帧重建几何则应改成「一次创建 + BufferUpdate」）

### 3.3 T3：机制上不适用

- **全部 `PackedStringArray`（147 处）**：`OS` / `DisplayServer` / `DirAccess` / `ResourceLoader` / `HttpClient` / `WebSocket*` / `SystemFont` / `TranslationServer` 等。元素是 `String`，封送成本 ≫ payload → 只能靠 C# 侧缓存解决。
- `MeshDataTool` 逐顶点 getter/setter、`FontFile.GetGlyphList`、`Skeleton3D.GetBoneChildren`：每次 1~几十个元素 → 「降调用次数」问题，不是桥。
- UI/编辑器类（`Theme` / `CodeEdit` / `TextEdit` / `RichTextLabel` / `ItemList` / `GraphEdit` / `Window` / `FileDialog` / `ColorPicker` / `VisualShader*` / `TileSet*`）。
- 单值/非帧：`ClassDB` / `ProjectSettings` / `Engine` / `RegEx` / `Expression` / `RandomNumberGenerator` / `ConfigFile` / `Translation`。

## 四、M0 实测清单（生死门，先做）

| 项 | 方法 | 验收/门槛 |
|---|---|---|
| ① 中转拷贝真实成本 | 在 4.4.1 与 4.7 上跑同一场景（gdex 四路基准或 CSBS），对照「C# 数组进 API」与「复用缓冲的桥」两条路径的 submit 段 | 产出 µs 级对照表；确认「省下的次数」是否与 §1.2 带宽一致 |
| ② 原生 `resize` + `free` 成本 | 1 MB / 8 MB / 32 MB 三档，在桥内只做「分配+释放」不做拷贝，与「复用缓冲」对照 | 得到每档 alloc/free 的 µs；这是当前**完全无实证**的一项 |
| ③ LOH / GC 代价 | 僵尸 `RenderingManager.cs:349-408`：加 `GC.GetTotalAllocatedBytes(precise:true)` 与 `GC.CollectionCount(2)` 探针，量「每帧 2.88 MB 分配」的实际代价 | 得到每帧 GC 时间占比；决定 P2 是否独立成立 |

**门槛判据**：若在目标场景中「①+②+③」合计收益 **< 5% 帧时间**，则项目缩为「只做 P3 回读 + 批量原语」，或终止。

## 五、验收方法（写入每次改动的 DoD）

1. **正确性**：`tests/` 逐字节比对（桥路径 vs 原生路径产出的缓冲一致）+ 回读一致性。
2. **收益**：A/B 开关（`FastBridge.Enabled`）同帧切换，输出 `fill/submit` 分段。
3. **零分配**：GFB 路径下 `GC.GetTotalAllocatedBytes(precise:true)` 前后差 = 0。
4. **无回归**：`Enabled=false` 时行为与未接入完全一致。
